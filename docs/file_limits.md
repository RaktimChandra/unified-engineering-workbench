# Tested file-size limits (Task B)

Both parsers enforce configurable limits (`wb::stl::Limits`, `wb::nodal::Limits`). Defaults:

| Limit | ASCII STL | Nodal CSV |
|---|---|---|
| Maximum file size | 256 MiB | 256 MiB |
| Maximum items | 5,000,000 triangles | 5,000,000 nodes |
| Upload body accepted by the local server | 256 MiB + 1 KiB | same |

Inputs over a limit are rejected before any geometry is published (`stl.too_large`,
`stl.too_many_triangles`, `csv.too_large`, `csv.too_many_nodes`). The message explains how to reduce
the file.

## Measured parse times

Generated by `wb_cli limits` (in-memory parse plus full validation and mesh diagnostics; release
build, GCC 13 `-O3`, Intel Xeon @ 2.10 GHz, 2 vCPU container):

| Kind | Items | File size | Parse + validate | Result |
|---|---:|---:|---:|---|
| STL | 1,000 triangles | 0.1 MiB | 0.001 s | accepted |
| STL | 100,000 triangles | 12.6 MiB | 0.11 s | accepted |
| STL | 1,000,000 triangles | 129.1 MiB | 1.42 s | accepted |
| STL | 2,500,000 triangles | 327.4 MiB | (rejected immediately) | `stl.too_large` |
| CSV | 1,000 nodes | 0.04 MiB | < 0.001 s | accepted |
| CSV | 100,000 nodes | 3.9 MiB | 0.017 s | accepted |
| CSV | 1,000,000 nodes | 39.9 MiB | 0.21 s | accepted |
| CSV | 4,000,000 nodes | 163.0 MiB | 0.90 s | accepted |

STL parsing includes vertex welding and the edge-manifold check (hash maps), which is why it costs
more per byte than CSV.

## Practical guidance

* The **rendering** side (three.js in the browser) is the practical bottleneck before the parser.
  About 1 M triangles or 4 M points stay interactive on a mid-range laptop GPU. Beyond that, frame
  rate drops but correctness does not change.
* Peak memory while parsing is roughly 3 times the file size: the request body, the parsed arrays
  and the transfer buffer.
* Empty files, whitespace-only files and header-only CSVs are explained explicitly (`stl.empty`,
  `csv.empty`, `csv.no_rows`). They are not reported as generic parse errors.
